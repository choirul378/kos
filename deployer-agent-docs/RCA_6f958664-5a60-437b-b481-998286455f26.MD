# RCA — kos-rental-1 build failure (run 6f958664-5a60-437b-b481-998286455f26)

## Summary
The deployment fails at the `build_image` step, in the `frontend-build` stage. Two distinct causes surfaced in sequence. The first was a manifest-level issue I fixed; the second is a **template ↔ codebase mismatch** that must be resolved in the source / deployment configuration by E1 + the user. It is NOT a manifest fix.

## Timeline of evidence

### Failure 1 (original run 892c15f7…) — node engine floor aborts yarn install
```
error @react-native/dev-middleware@0.86.3: The engine "node" is incompatible with this module.
Expected version "^20.19.4 || ^22.13.0 || ^24.3.0 || >= 25.0.0". Got "20.19.2"
error Found incompatible module.
```
The frontend base image ships node 20.19.2; a transitive dep demands >=20.19.4, and yarn classic aborted (exit 1).

**Fix applied (manifest, by me):** added `--ignore-engines` to every `yarn install` invocation in `Dockerfile`, `Dockerfile.cloudbuild`, and `build-frontend-artifacts.sh`. The offending package is a dev-middleware that does not affect the production bundle, so ignoring the engine floor is safe. This worked — on the retry, `yarn install` completed cleanly (`Done in 40.68s`).

### Failure 2 (run 6f958664…) — `yarn build` script does not exist
After install succeeded, the build advanced to `yarn build` and failed:
```
yarn run v1.22.22
error Command "build" not found.
```

## Root cause (definitive)
The deployment template is **`fastapi_react_mongo_shadcn_base_image` (farm)**, whose Dockerfile hardcodes `yarn build` to produce a static web SPA served by nginx/Cloudflare. But the frontend in this codebase is a full **Expo / React-Native app**, not a web React app. Confirmed by direct source inspection of `/app/scratch/frontend`:

- `package.json` → `main: "expo-router/entry"`; dependencies `expo@57.0.25`, `expo-router@57.0.23`, `react-native@0.86.3`, `react-native-worklets`, `babel-preset-expo`.
- `package.json` scripts are Expo-only — **there is no `build` script**:
  ```json
  { "start": "expo start", "android": "expo start --android",
    "ios": "expo start --ios", "web": "expo start --web", "lint": "expo lint" }
  ```
- Expo project markers present: `app.json`, `eas.json`, `metro.config.js`, `expo-env.d.ts`.

An Expo project does not produce a static web bundle via `yarn build`, so the farm template cannot build or serve this frontend.

## Verification status
- Failure 1 fix (`--ignore-engines`): **verified** — the subsequent build passed the install step.
- Failure 2 root cause: **verified by static source inspection**. I attempted to verify an Expo web-export path (`expo export --platform web`) in the eph sandbox, but the pod was OOMKilled during the (very large) Expo `yarn install` before I could run the export, so web-export viability is **unverified**.

## Recommended fix — owner: E1 + user (Code / deployment-config decision)
This is an architecture/template decision, so pick one:

**Option A (preferred if a NATIVE mobile app is the intent):** Redeploy on an Expo-family template (`expo_mongo_base_image`, `expo_mongo_base_image_eas`, or `mono_fullstack_base_image`) instead of farm. The farm template is for web SPAs and structurally cannot serve an Expo frontend. Note Expo apps are tunnel/EAS-targeted and are not web-deployable with custom domains the way farm apps are.

**Option B (only if a WEB deployment on farm is genuinely intended AND the app is web-compatible):** Add a web build script to `frontend/package.json`, e.g.
```json
"build": "expo export --platform web"
```
`expo export --platform web` emits a static site to `dist/`, which the farm Dockerfile already handles (it maps `dist/` → `build/`). **Caveat (unverified):** this app uses native-oriented modules (`react-native-worklets`, `expo-router`) that may not export/run cleanly on web; this path must be built and smoke-tested before relying on it.

## What I changed and what I did NOT change
- Wrote the full farm manifest set to GCS with `--ignore-engines` added (necessary and correct — keep it; it's required for the install to pass regardless of which option is chosen).
- I did **not** modify any application source, and I did **not** hack the farm Dockerfile to force an `expo export`, because the correct resolution is a template/source decision owned by E1 + the user, not a speculative manifest override on a mismatched deployment.
